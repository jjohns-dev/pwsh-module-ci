# 6. Host the build harness in this repo and configure it by input, settings file and manifest

## Status

Accepted — 2026-11-10

## Context

- Seven `jjohns-dev` module repos each vendor four `Build/` files. Measured 2026-10-26: 5–6 distinct variants per file; only `PS.GitHub` and `PS.GHOps` are byte-identical across all four.
- Fixing one CI problem takes N pull requests. Two weeks of rollout work across #17, #22, #23, #24 and #27 is the evidence, and the maintenance burden — not the drift itself — is what forces this.
- Classifying `Build/PSScriptAnalyzerSettings.psd1` on 2026-11-05 found the divergence largely illusory: three of its four variants are behaviourally inert (`Rules = @{}`, `IncludeDefaultRules`, `Severity` ordering), and three of its five `ExcludeRules` suppress nothing in any repo. The cost is real; most of the variation is not.
- `job.workflow_repository` and `job.workflow_sha` let a reusable workflow check out its own source at the exact commit being run. This is a documented pattern, not a workaround, and it pins the harness to the workflow version automatically. Proven by the self-checkout spike, run [42090065876](https://github.com/jjohns-dev/PS.Log/actions/runs/42090065876).
- The consumers' own `AGENTS.md` files tell agents to run `./Build/build.ps1` locally (PS.Log, AWSAutomation, SecurityTools; measured 2026-11-09). A setting that changes the build — a tag exclusion, an analyzer exclusion, strict mode — must therefore reach local runs too, which a workflow input cannot do.
- The 2026-11-09 shim spike showed a single fleet-identical `Build/build.ps1` can read the harness version from the repo's own `ci.yml` caller, keep a cached clone at that version, and forward every argument, so local runs use the same harness as CI.
- End-to-end proof, 2026-11-10 (task C5 of the centralized-harness spec): PS.GHOps, PS.SSL and SecurityTools ran all three workflows on the harness at `a3e5f5c` with executed test counts equal to their baselines, unchanged required check names, and a dry-run release matching PS.GHOps' last real release apart from commits made since.
- `SecurityTools` cannot consume `ci.yml` today for one reason: `os-matrix` is a JSON array of strings, and it needs `os`, `pesterScope` and `minTests` travelling together per runner.
- The genuinely per-repo configuration found so far is small: `AWSAutomation` needs `PSUsePSCredentialType` and `PSAvoidUsingPlainTextForPassword` excluded, because `AWS.Tools.*` authenticates with `Amazon.Runtime.AWSCredentials` and never `PSCredential` — verified against `AWS.Tools.Common` 5.0.318, where zero cmdlets take a `PSCredential`-typed `-Credential`.
- **Measured 2026-11-06 (run `42295351419`), and it changed the input shape.** An earlier draft of this ADR added a second input, `os-matrix-include`, beside `os-matrix`. A five-probe spike showed that when `include:` and `os:` coexist, an `os` leg matched by no include entry still runs, carrying empty values. So a caller supplying the include list but forgetting to narrow `os-matrix` gets a silent extra leg whose empty `PesterScope` falls through to the psake default `All` — the same silent-wrong-behaviour #9 exists to prevent. The same run showed that a single polymorphic input normalized by a setup job cannot be inconsistent, that existing string-array callers are unaffected, and that `needs` resolves at `strategy` scope.

## Decision

- `Build/` moves into this repo. The reusable workflows check it out via `job.workflow_sha` and run it against the caller's checkout.
- Per-repo variation lives in exactly three declared places, never in vendored copies of the harness:
  - **workflow inputs**, for the CI matrix (`os-matrix`, `min-tests`);
  - an optional **`Build/harness.psd1`**, for build behaviour that must also reach local runs, restricted to `PSScriptAnalyzerExcludeRules`, `PesterExcludeTag` and `PesterStrictMode`; an unknown key fails the build;
  - the module **manifest**, for runtime modules (`RequiredModules`).
- Each consumer keeps one fleet-identical `Build/build.ps1` **shim** for local runs. It reads the harness version from the repo's `ci.yml` caller and hands off to the harness. CI never runs it: the reusable workflows check out the harness themselves.
- **`os-matrix` becomes polymorphic, normalized by a `normalize` job.** It accepts either its current JSON array of OS-name strings or a JSON array of objects carrying `os` and optionally `pesterScope` and `minTests`. A small `normalize` job converts the former into the latter and emits it as a job output; `validate` builds `matrix.include` from that output. **No second input is added.**
- **#21's option A — extend `ci.yml` rather than add a second workflow.** #21's option B is rejected: its technical hedge is no longer needed, and it would create a sixth copy of the `Verify Pester results` step when only two of the existing five are covered by the drift guard in `tests/VerifyPesterResults.Tests.ps1`.
- `SecurityTools` is the design target for the input shape, not the final migration. It is the only repo that exercises per-runner variation, so designing against it last would mean designing the input twice.
- Consumers keep a thin workflow stub, because GitHub requires a workflow file in each repo to bind to that repo's events.

## Consequences

- One edit fixes every consumer. The harness and the workflow can no longer drift apart, because `job.workflow_sha` resolves to the commit of the workflow actually running.
- **Blast radius grows sharply.** A bad harness commit reaches the whole fleet through the moving major tag with no staging environment. The existing rule — stage behind an immutable `vX.Y.Z` pin — becomes more important, not less.
- **A repo's build is now described in four places, not one:** the harness here, its caller YAML, its optional `harness.psd1` and its manifest. Each is small and declared, but a reader has to know all four exist.
- **Every consumer carries one file it must not edit.** The shim is byte-identical across the fleet; the harness warns when a consumer's copy has drifted from `templates/Build/build.ps1`, but does not fail.
- **GitHub Enterprise Server is excluded** for as long as this stands: the `job.workflow_*` properties are documented as unavailable there.
- **`os-matrix`'s accepted type is widened, not changed.** Existing callers pass a JSON array of strings and keep working — measured in the spike, not assumed. Under ADR-0002 the call does not stop working, so this is a minor. Widening rather than adding a second input also leaves no deprecation tail, which the earlier two-input draft would have created: both inputs would have had to be carried until one was retired.
- This repo acquires a PowerShell harness it has never had, and therefore needs real tests for it. When this was written the test harness covered exactly one `run:` block; since #59 it is a set of Pester suites in `tests/`, one per `run:` block with real logic, which is where tests for the moved `Build/` files belong.
- Debugging moves further from the consumer. A failing build is no longer explained by files in the repo being built, which is worse for a newcomer even though it is better for maintenance.
- **#21's implementation traps apply, with two corrections.** Still binding: pass caller-supplied values through `env:` rather than interpolating them into a `run:` block, because centralising turns a local literal into untrusted input; branch on an empty matrix key instead of passing `@{ PesterScope = '' }`; and update each repo's ruleset in the same change, because adopting a reusable workflow renames the required checks and the old names simply stop reporting. Two traps carried here from an earlier draft were measured against `SecurityTools`' live `validate.yml` on 2026-11-06 and are **not** true of it: it uses `if-no-files-found: warn`, exactly as `ci.yml` does, so there is nothing stricter to preserve; and it already sets `timeout-minutes: 15`. Measured in the same spike: `ci.yml` sets `name: validate (${{ matrix.os }})` explicitly and `matrix.os` stays populated under include-form, so the six existing consumers' required check names do not change — the ruleset trap applies to `SecurityTools` adopting the workflow, not to this shape change.
- **This does not settle #19, and the earlier framing of it here was too strong.** Centralising yields *one* hand-rolled harness instead of seven — still hand-rolled. #19's argument is not about any single defect but about recurring maintenance: Sampler's curated Pester task already encodes the `FailedCount` gap that `ci.yml`'s verify step exists to catch, and ships it maintained. That benefit persists whether or not the harness is centralised here.
- Against that, #19 also records three things Sampler's defaults do **not** provide and that this repo already has: a per-leg test-count floor (no equivalent concept in Sampler), an OS matrix (its default pipeline is a single job), and `JUnitXml` output with the artifact guards that exist because `dorny/test-reporter` mis-parses Pester's NUnitXml v2.5. Hand-rolling keeps all three by construction. The real choice is therefore maintained tasks that must be adapted against hand-rolled tasks that must be maintained — not centralise-or-Sampler.
- Sampler would additionally require a per-repo layout change, since it resolves `SourcePath` from a manifest in `source`, `src`, or a module-named folder, and expects `build.yaml`, `RequiredModules.psd1` and `Resolve-Dependency.ps1` at each repo root. These repos keep the manifest at the repo root beside `Public/` and `Private/`. So adopting it later still costs an N-repo edit, which is the cost this decision exists to remove.
- #19's sequencing step 3 — audit `build.psake.ps1` against **Sampler's** equivalent tasks — remains outstanding. The #20 classification audited the seven repos against *each other*, which is a different question and does not answer it.
